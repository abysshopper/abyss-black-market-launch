# Token designs and operations

This is a factorized catalog of the public launch design space, not a menu of preapproved launches. **SDK representation, example coverage, implementation support and current execution admission are different facts.** A token/reward choice must intersect valid token parameters, fee-asset accounting, market/profile capabilities, registry eligibility, funding, topology and exact sequential execution proof. An example or successful encoding establishes none of the remaining facts.

Use [hooks.md](hooks.md) for hook/profile semantics, oracle/fee modes, fixed versus dynamic offerings and release-specific compatibility, and [hmm.md](hmm.md) for HMM strategy configuration and operations. Use the skill's workflow for exact pricing, authorization, funding and recovery; this reference deliberately does not duplicate addresses, ABI tuples, deployment IDs or pricing formulas.

## 1. Token kind × reward mode

The wire enums contain two token kinds and three **token-global, mutually exclusive** reward modes. The following six combinations have implementation paths; that does **not** make every venue/hook/quote/fee/funding combination valid.

| Kind × mode | Meaning | Additional constraints / example evidence |
| --- | --- | --- |
| ERC20 × None | Fixed-supply fungible token with no reward module. Collected fees can pay owner credits and, for launched-token fees, burn. | Positive raw supply up to `2^256 - 1`; every fee policy has `rewardsBps = 0`. Examples cover V4, Abyss, mixed burn, multiquote and deeper V4 ranges. |
| ERC20 × Staking | A separate multiasset staking module distributes streamed fee rewards to staked-token entitlements, not merely to wallet holders. | Raw supply at most `10^77`; at least one fee asset has a positive rewards share. Example: two V4 positions, two ordered buys, staged. |
| ERC20 × Dividends | Streamed multiasset rewards are embedded in the token and accrue to eligible holder balances; no staking deposit is needed. Transfers/burns checkpoint ownership. | Raw supply at most `10^77`; at least one positive rewards share; protocol/custody exclusions are finalized before eligible transfers. Abyss-only and multiquote mixed examples. |
| ERC404 × None | Fixed-supply fungible token paired with a real ERC721 mirror (pinned DN404/ERC7631 implementation), with no fee reward module. | Raw supply fits uint96; NFT-unit/count bounds below; every rewards share is zero; each selected launch profile needs ERC404 capability. V4 and Abyss examples. |
| ERC404 × Staking | ERC404 fungible principal can use the separate staking module; rewards follow stake entitlements rather than NFT ownership alone. | **Implementation-supported, no shipped case.** The parameter validator permits it, the factory selects `deployStaking` by reward mode for either token kind, and shared context accepts the separate module. Requires ERC404-capable profiles, NFT bounds and positive rewards shares. Do not claim example-tested or currently admitted. |
| ERC404 × Dividends | Embedded holder dividends checkpoint the same underlying balances for fungible transfers, burns and direct mirror transfers; NFTs are not an independent second reward share. | ERC404 bounds/capabilities and positive rewards shares; excluded infrastructure does not gain holder rewards. Example: two V4 plus three Abyss positions, staged. |

The ERC404 staking row is grounded in the [parameter validator](https://github.com/abysshopper/abyss-hooks/blob/main/contracts/protocol/src/launch/lifecycle/v1/tokens/LaunchTokenParametersV1.sol), [factory `createRewards`](https://github.com/abysshopper/abyss-hooks/blob/main/contracts/protocol/src/launch/lifecycle/v1/tokens/LaunchLifecycleTokenFactoryV1.sol) and [context `configureRewards`](https://github.com/abysshopper/abyss-hooks/blob/main/contracts/protocol/src/launch/lifecycle/v1/tokens/LaunchTokenContextV1.sol), not inferred from enum cross-products. ERC404 transfer semantics are in [LaunchERC404V1](https://github.com/abysshopper/abyss-hooks/blob/main/contracts/protocol/src/launch/lifecycle/v1/tokens/LaunchERC404V1.sol).

### Token parameters and reward semantics

- **Decimals:** current lifecycle tokens use 18 decimals, as verified by both example runners. `TokenConfigV1` has no decimals field. Quote decimals are independently read; a generic SDK fixed-supply-token constructor with a decimals argument is **not** the lifecycle factory interface. Do not advertise configurable lifecycle decimals.
- **Supply:** all bounds above are raw integer units, not whole-token counts. Supply must be positive. Current examples choose ERC20 `1,000,000 × 10^18` and ERC404 `10,000 × 10^18`; these are recipes, not mandatory supply values. The lifecycle mints the entire committed initial supply to core inventory; no public postlaunch mint path exists. Market budgets cover it exactly. Mint-rounding leftovers burn before opening buys, not to a creator reserve.
- **ERC20:** `nftUnit` must be zero and onchain `metadataURI` empty. Description, socials and optional artwork belong to the API metadata flow, not this token field.
- **ERC404:** supply and NFT unit each fit uint96; unit is at least `10^18` raw units (one fungible token). `floor(supply / nftUnit)` must be **1–10,000**. The validator does not require exact divisibility; do not invent it. Example unit is `100 × 10^18`, giving 100 maximum NFTs. Actual mirror balances/materialization depend on the DN404 implementation, not just this theoretical maximum. `metadataURI` is the NFT base URI; an empty URI does not provide hosted NFT metadata.
- **Identity/metadata bounds:** the lifecycle planner requires name 1–128 UTF-8 bytes, symbol 1–32 bytes, metadata URI at most 2,048 bytes. Example runners add their own normalization/codepoint checks. `inventoryRecipient` must be nonzero and not core; this cancellation-policy field does not allocate an active creator reserve.
- **Reward assets:** the immutable set is the sorted fee-policy assets with positive rewards shares, up to eight. It can include the launched token and/or supported quotes. Reward-free plans cannot have a positive rewards share; reward-enabled plans must have at least one, but not every collected asset must reward holders/stakers. There is no public-plan field for an arbitrary extra rewards token or duration.
- **Duration/accounting:** [MultiAssetStreamV1](https://github.com/abysshopper/abyss-hooks/blob/main/contracts/protocol/src/launch/lifecycle/v1/modules/MultiAssetStreamV1.sol) releases each asset over **seven days**; an active-stream top-up preserves its finish. Emissions with no eligible share supply queue instead of retroactively rewarding nonexistent holders. This is not guaranteed yield/APY or a configurable launch reward duration. Only the configured distributor can notify prefunded rewards.
- **Staking:** [MultiAssetStakingV1](https://github.com/abysshopper/abyss-hooks/blob/main/contracts/protocol/src/launch/lifecycle/v1/modules/MultiAssetStakingV1.sol) maintains nontransferable stake entitlements; the staked principal is not reward funding, even when that token is a reward asset. Depositing/withdrawing principal and claiming streamed rewards are distinct actions. See the public-interface limitation in section 4 before promising SDK staking commands.
- **Dividends:** infrastructure exclusions (including token/core/factory/hub/module and launch market exclusions) are finalized once; balance mutations checkpoint accrual. There is no user-configurable holder blacklist in the plan. A current registered fee owner can set a separate dividend payout bounty up to 1,000 bps; third-party claims pay beneficiary net plus caller bounty, while self-claims receive gross. Staking claims do not use this dividend bounty.

### Fee allocation is orthogonal to reward mode

**Burn is not a fourth reward mode, and fee allocations are not trading taxes.** For each collected fee asset, commit unique ascending nonzero asset addresses and `ownerBps + rewardsBps + burnBps = 10,000`. Nonzero burn is allowed **only for the launched token**, never WETH/USDG/arbitrary quote assets. External fee assets need actual code and compatible exact transfers; catalog membership is not approval.

The example reward allocation is 4,000 bps rewards / 6,000 owner. The burn example uses reward mode None and 3,000 bps burn on launched-token fees only; quote fees have zero burn. Those numbers describe shares of **collected fees**, not a 40%/30% tax on every transfer or trade. Custom public plans can select other valid shares, including rewards plus launched-token burn, subject to the full constraints. Python's fixed example helper does not expose every such mix.

Keep these economic layers separate:

1. Market LP fee and hook fee (pips), plus hook-specific fee asset/direction accounting.
2. Hook protocol/treasury share with its actual denominator.
3. For HMM markets, the collector diverts the selected share of **newly collected quote fees** to its per-market strategy manager before forwarding the remainder to the hub. Token-side fees and preexisting collector balances are not strategy funding.
4. Fee hub executor bounty (bps, at most 1,000), then owner/rewards/burn policy with canonical dust allocation on proceeds delivered to the hub.
5. Source-frozen developer/author fees, floor-rounded out of that source's owner portion, constrained by reviewed and protocol ceilings.
6. Independent dividend claim bounty, if configured.

V3 harvest snapshots the current executor rate across all sources, even already accrued fees. Policy shares and source-frozen developer terms remain immutable; changing executor bounty does not rewrite them. Existing owner credits remain with the credited owner. Stable author identity is distinct from its live payout route. See [V3 fee semantics](https://github.com/abysshopper/black-market-node-sdk/blob/main/docs/launch-lifecycle.md#stable-author-apis-and-v3-fees) and [hooks.md](hooks.md). Neither fee-allocation edits nor a new payout route change token reward mode after launch.

The [Node HMM guide](https://github.com/abysshopper/black-market-node-sdk/blob/main/docs/launch-lifecycle.md#090-release-hmm-pool-hooks), [Python HMM guide](https://github.com/abysshopper/black-market-python-sdk/blob/main/docs/launch-guide.md#hmm-launch-configuration) and [`HMMFeeCollectorV1.collect`](https://github.com/okjintao/black-market/blob/1ca98813f7aa72393116aac4d3d791e65d4fb635/contracts/src/launch/hmm/HMMFeeCollectorV1.sol) establish this quote-fee diversion. The collector floor-rounds the selected quote share, funds the manager, then forwards the remaining token/quote proceeds to the hub; preexisting collector balances are not swept into funding. `strategyShareBps` / `strategy_share_bps` is **0–10,000 bps of newly collected quote fees**, not a trade tax, an extra minted-token allocation or a fourth token reward mode. The remaining fees still use normal policies totaling 10,000 bps; do not promise the original gross quote-fee amount to owners/rewards while also funding HMM. A 100% strategy share can leave no quote proceeds from that source for normal dispositions. The strategy bids and resells separately acquired inventory and never touches permanent launch positions; economic gains, yield and price support are not guaranteed. Initial share/strategy configuration belongs in the reviewed plan; the fee owner's later share adjustment is a distinct operation, not a mutable launch allocation. See [hmm.md](hmm.md).

## 2. Market composition: intersecting dimensions

A custom public plan composes the following dimensions, not arbitrary smart-contract behavior.

| Dimension | Public design space | Intersections / exclusions |
| --- | --- | --- |
| Venue | Uniswap V4, Abyss, or a launch containing both. | Each market has its own exact adapter/profile/version/config. A V4 profile does not admit Abyss, or vice versa. |
| Hook/profile | Supported registered topology/schema, with required token-only, empty-preparation, permanent-custody and canonical-fee capabilities. | ERC404 additionally needs ERC404 capability; multiple positions need suitable capability/bounds. Use [hooks.md](hooks.md), not copied profile IDs. Shared V4 config4 and pool-bound config5/config6 are distinct interfaces with matching graphs; historical codec support is not current deployment support. HMM Fixed/Dynamic have their own collector/deployer/locker graphs, not aliases for non-HMM offerings. |
| Fee/oracle policy | LP/hook rates, registered spacing and oracle, fee mode and admitted author terms; external-liquidity policy where exposed. | All must fit the selected reviewed profile. Oracle protection is required by this skill; do not downgrade to a non-oracle offering. Fixed and dynamic are different offerings. Dynamic Fee Hook and both HMM offerings require zero LP fee and zero developer fee. HMM Fixed is oracle-free and therefore excluded here; HMM Dynamic is an oracle-enabled candidate, not automatically admitted. Encoding config6 alone selects none of these behaviors. |
| HMM strategy | HMM Fixed/Dynamic config6 adds an explicit typed `hmmLaunchConfig` / `hmm_launch_config` with quote-fee share, bid/ask geometry, stale handling, harvest/deploy thresholds, inventory/exposure limits and optional premium decay. | The matching codec appends the required canonical 448-byte tail; the full plan hash binds it, and salt mining preserves it. A plain config6, missing/extra tail or tail on a non-HMM profile fails. Thresholds use real raw token/quote units; unknown quotes require explicit quote thresholds. This does not authorize spending initial quote inventory or withdrawing locked LP. See [hmm.md](hmm.md). |
| Quote assets | Multiple real quote assets with actual chain identity, code, decimals and balances. Public lifecycle quote/fee assets are not limited to example WETH/USDG symbols. | At most **one V4 market per quote across all topologies/fees/salts**; put multiple positions in it. Abyss may also use that quote. Duplicate canonical market identities and invalid source-asset accounting remain refusals. Quote catalog metadata/pricing seeds do not establish admission. |
| Allocation | Positive token budget per market; ordered positive-liquidity positions with exact token caps. | Market budgets sum exactly to initial supply; position caps sum exactly to their market budget. Initial mint requires **zero quote deposit** at actual opening orientation. Shared-endpoint capacity, integer limits and profile bounds still apply. |
| Position shape | One-sided single range or public range helpers: `staircase`, `early-scarcity`, `smooth-ramp`; exact count, spacing, adjacent coverage and extended final tail. | Every new market needs its own funded permanent boundary tail and continuous opening-to-tail coverage. `source-gaps` helper output can conflict with this policy; use adjacent ranges. A tail in another market is not coverage. The four-position example is Early Scarcity, not an eight-position catalog reproduction. |
| Opening valuation | Each market uses whole minted supply and its own quote/orientation, aligned by SDK integer helpers. | Mixed/multiquote markets target the same reviewed USD valuation, not the same raw sqrt price. Do not use a divided market budget as total supply or duplicate pricing math here. |
| Initial buys | None or ordered buys naming market, quote input, recipient, positive minimum output and price limit. Repeated market indices preserve order. | Funding must cover the sum of buys sharing a quote. Every buy is part of indivisible activation. Stateful outputs—not independent first-buy estimates—derive protection. Current planner requires positive minima; do not promise a zero-minimum switch. |
| Funding | Direct ERC20, canonical native wrapping, admitted swap conversion. | Exact escrow approval/balance/native value and conversion commitments matter. Swaps require admitted input/target/spender/code/calldata; wrapping is not a swap. The fixed wrappers fund WETH by wrapping and other quotes through admitted conversion, not arbitrary wrapper-selected routes. |
| Execution | Explicit atomic or staged. | Atomic is one core launch transaction after prerequisites. Staged splits only empty market preparation; activation (all mint/lock/burn/buys/opening) cannot split. No automatic mode fallback. |

Global shape bounds: **1–16 markets, 1–8 fee assets, at most 8 funding outputs, 64 ordered buys and 32 total positions**, tightened further by each selected profile and live gas/calldata constraints. These are not guarantees of executable size. Deadline/expiry, actual oracle readiness, eligibility, transfer behavior, prices/funding and sequential execution remain current-state conditions. A plan supported by the types but refused/unavailable in admission is not launchable.

Sources: [current codecs](https://github.com/abysshopper/black-market-node-sdk/blob/main/docs/launch-lifecycle.md#current-venue-codecs), [allocation/topology helpers](https://github.com/abysshopper/black-market-node-sdk/blob/main/src/launch.ts), [planner validation](https://github.com/abysshopper/black-market-node-sdk/blob/main/src/lifecycle/planner.ts), [contract validation](https://github.com/abysshopper/abyss-hooks/blob/main/contracts/protocol/src/launch/lifecycle/v2/LaunchPlanValidatorV2.sol).

### Counting families without certifying combinations

The six token-kind/reward-mode combinations in section 1 are unchanged. The known SDK catalog now contains **eight families**: four Abyss variants, V4 fixed, V4 Dynamic Fee Hook, HMM Fixed and HMM Dynamic. Under this workflow's oracle requirement, only **five** are family-level candidates: Abyss Standard Oracle, Abyss Quote Oracle, V4 fixed with certified oracle behavior, V4 Dynamic Fee Hook and HMM Dynamic. HMM Fixed is oracle-free, alongside Abyss Standard/Quote (variants 0/2), and cannot become oracle-enabled merely by encoding registered oracle fields.

Thus **6 × 5 = 30 conditional token/reward × oracle-enabled-family candidates** (previously 6 × 4 = 24); **6 × 8 = 48** includes all known families, including the three policy-excluded non-oracle ones. **6 × 6 = 36 is not the oracle-permitted count**: it would incorrectly include HMM Fixed. These are catalog intersections, not proved launches, exhaustive economic designs or live-valid combinations. They do not multiply fee modes, quotes, range counts or mixed-market compositions, and every intersection still requires actual token/reward/asset compatibility, live profile admission and exact-plan proof. Sources: [Node known presets](https://github.com/abysshopper/black-market-node-sdk/blob/main/src/lifecycle/presets.ts), [Python known presets](https://github.com/abysshopper/black-market-python-sdk/blob/main/black_market_sdk/lifecycle_presets.py), and oracle implementation qualifications in [hooks.md](hooks.md).

The [HMM Fixed review](https://github.com/okjintao/black-market/blob/1ca98813f7aa72393116aac4d3d791e65d4fb635/contracts/hooks/hmm-fixed/review.md) explicitly states that Fixed has no truncated-oracle read interface or history; [HMM Dynamic source](https://github.com/okjintao/black-market/blob/1ca98813f7aa72393116aac4d3d791e65d4fb635/contracts/hooks/hmm-dynamic/HMMDynamicHook.sol) composes `PoolBoundTruncatedOracleV3`. This implementation distinction overrides any inference from the existence of oracle fields in both configuration schemas.

### Explicit unsupported / unestablished designs

- Unsupported token kind/reward enum, simultaneous staking and dividends on one token, adjustable lifecycle decimals, postlaunch public minting, arbitrary transfer taxes, mutable hidden supply or a user blacklist are not public lifecycle-plan options.
- Nonzero ERC20 NFT fields, zero/over-bound supply, invalid ERC404 units/NFT counts, reward-free positive reward allocations, reward-enabled all-zero reward allocations, quote-asset burn and non-10,000-bps policy totals are invalid.
- Two V4 markets using the same quote, quote-funded two-sided initial LP, under/overallocated supply, omitted/funding-deficient buys and split activation are not supported by this lifecycle construction.
- Unregistered/custom Solidity hooks, unsupported schemas, mismatched inner/outer config/profile/version/terms, retired/disabled profiles and unsupported funding conversions cannot be made valid by an example label or codec.
- HMM Fixed cannot satisfy this workflow's oracle protection; registered oracle configuration fields do not add an oracle to its implementation. Neither HMM offering supports nonzero LP/developer fees or an omitted/noncanonical tail. A strategy share does not relax fee-policy totals, permit quote burn or change token-global rewards. Public HMM configuration is not blanket permission to retune the whole strategy postlaunch; expose only operations established by the actual public interface.
- ERC404 staking, additional quote assets, other fee-policy mixes and other position counts have no claim of shipped end-to-end example coverage here. They require consumer-local public-plan construction and real admission; absence of an example is not an exclusion. Any combination not settled by the public interfaces and live evidence stays **unknown**, not presumed valid.
- Active launches cannot be creator-paused/cancelled, and permanent launch liquidity cannot be treated as withdrawable creator LP. Trading activation does not establish lending-feed maturity or lending collateral eligibility.

## 4. User-visible operations

### Public-interface levels

- **Lifecycle helpers** discover/read/prepare/prove/build unsigned launch commands; they do not sign, broadcast or publish.
- **Exported contract ABI operations** can be called/encoded with the caller's public chain client and wallet. ABI availability alone is not a turnkey lifecycle planner, a permission grant or live simulation admission. This catalog names operations but does not copy ABI definitions.
- **Contract-only capability** is explicitly labeled where the inspected SDK exports omit the operation. Do not invent a helper or ABI export for it.
- **HTTP API operations** have their own signed authorization/capability/session/indexing requirements; chain success is not API success. Python exposes some postpublication methods not present in the inspected Node client.

### Launch phases, funding and recovery

| Operation | What it does | Authorization / state restrictions |
| --- | --- | --- |
| Discover profiles/deployment; predict token; serialize/hash plan | Resolve supported construction interfaces, inspect current profiles, determine identity and retain exact portable commitment. | Read-only/pure; prediction, release presets and encoding are not admission. Economics cannot change after begin; execution mode/batching are metadata outside the economic tuple. |
| Prepare and plan | Finalize bound hook salts and, when requested, statefully derive protected ordered buys; prove exact explicit atomic/staged plan. Node `prepareAndPlanLifecycleLaunch`; Python `prepare_and_plan_lifecycle_launch`. | Unsigned; buy reprotection/salt finalization belong to an unstarted plan, not a regeneration of a begun commitment. Refused/unavailable proof stops execution. |
| Construct/validate HMM configuration | Node public `HmmStrategyConfig` / `HmmLaunchConfig`, `defaultHmmLaunchConfig`, tail encode/decode/validate helpers; Python snake-case counterparts. Matching market codecs append the typed tail. | Pure construction/validation, not a transaction or launch admission. Defaults are examples calibrated to market budget and known quote units, not agreed economic policy. Full plan review/proof still applies; HMM Fixed remains excluded by oracle policy. |
| Plan finalized plan / resimulate | `planLaunch` / `plan_launch` admit an already finalized commitment; `simulateLaunchPlan` / `simulate_launch_plan` freshly prove remaining work. | Read-only source chain; preserve receipt context and original mode/confirmations during continuation. Generic EVM controlled forks are separate disposable backends, not authority for Robinhood Nitro admission. |
| Approval/reset prerequisite | Set exact funding-escrow allowance, reset insufficient nonzero allowances where required. | Creator/payer signs; spender is escrow, not core/adapter. No funding approval is permission to change route or spend arbitrary amounts. Native wrapping needs exact native value instead. |
| Atomic launch (`launchAtomic`) | Deploy token, fund/prepare empty infrastructure, mint/lock all positions, burn rounding leftovers, execute ordered buys and open public trading in one core transaction. | Creator-bound exact commitment, prerequisites, live profile/deadline/funding/execution checks. Activation effects roll back together on failure. |
| Begin staged (`beginLaunch`) | Freeze commitment/mode and create inactive token/reward/fee context and funding; enters Preparing with no prepared markets. | Creator-bound, unstarted launch; no eligible public transfer/trading yet. Begin is not completion or API publication. |
| Prepare (`prepareMarkets`) | Prepare contiguous **empty** market infrastructure; advances prepared-market count; all prepared becomes Ready. | Committed creator/domain and exact ordered batch; only SDK-classified compute/gas-envelope capacity may subdivide empty preparation. No mint/buy/position omissions and no automatic fallback. |
| Activate (`activateLaunch`) | From Ready, verify canonical opening state, mint/lock/seal every position, burn leftovers, execute every buy and irreversibly activate token/public markets. Activating is a transient phase, not another user step. | Same frozen commitment; all activation remains one transaction. Manipulated opening state/preactivation liquidity fails; token remains inactive and Ready/cancellable. No later creator pause. |
| Read progress / build next | `readLaunchProgress` / `read_launch_progress` reconcile canonical/head state, market state, confirmations, receipt/replacement/reorg evidence and nonces. `buildNextTransaction` / `build_next_transaction` returns one freshly proven unsigned immediate envelope. | Exact original plan/mode/policy/evidence; pending or unconfirmed work waits without new executable commands. A moved/removed inclusion, revert or replacement-cancellation is not completion. Optional submission preflight is read-only, not wallet authorization. |
| Cancel | Build next with `action: "cancel"`; terminally cancel Preparing/Ready and refund unspent external funding. | Separate explicit authorization, creator-bound stored commitment; still requires fresh execution/receipt/nonce safety. Available after expiry/profile retirement without adapters/new profile/funding admission. Active and Cancelled are terminal. Wrapped-native refunds are wrapped tokens, not native gas; unrelated donations/launch funds are not swept. |
| Resume existing run | Reconcile and continue only remaining proven Preparing/Ready work, or verify/publish an already Active launch using the original run/session/receipts. | Explicit live continuation, not dry run or fresh plan. Preserve salts, token identity, buys/minima, deadlines and exact signed-hash evidence. Cancelled does not resume; ambiguous sends do not authorize blind resend/relaunch. |

`burnOnCancel` determines whether remaining cancelled core token inventory burns or stays permanently inactive; it does not unlock a public tradable reserve. Cancellation is not an automatic recovery fallback.

| Inspect permanent custody / collect locked-position fees | V4 locker getters show sealed state, position count and fee recipient. | Harvest and split (`claimAndSplit()`) | No-argument fee hub operation collects registered sources, pays executor bounty, credits owner/developer portions, notifies rewards and burns permitted launched-token portion. | Permissionless for a valid executor recipient after hub finalization: zero/hub/rewards/asset/system/source-custody recipients are excluded.
